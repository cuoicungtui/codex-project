- (direction) Product aims to build a workspace harness where frontier models author or update skills, then a small-model runtime executes them with full logging, evaluation, and feedback.
- (constraint) v1 stays filesystem-first with no production database, no multi-user auth, and no large UI surface.
- (capability) The system must ingest a skill folder and surface its markdown, metadata, examples, tests, and assets for downstream runtime and evaluation.
- (capability) The system must run a selected skill through a Python runtime using a small model configured from environment variables rather than hardcoding provider or model choice.
- (capability) The system must persist each run as a replayable folder with run metadata, trace, outputs, logs, and evaluation artifacts.
- (capability) The system must evaluate a run against test cases or checks, score it, and generate feedback for the next skill revision.
- (assumption) The first version is a developer-facing hackathon product, so visible operational traceability matters more than polished UX.
- (question) Which small-model providers must be supported in v1?
- (question) What is the minimum required skill metadata schema beyond SKILL.md?
- (question) Should raw prompts and tool calls be captured by default or only in debug mode?
